Logic Explanation

Lifecycle when adding loot then syncing: When a user adds an item, addLoot() checks the input first, then adds the item object to lootItems. After that it calls saveState() to save the data in localStorage, then updateUI() to show the changes on the page. When the user clicks Sync to Server, syncToServer() calls getStateObject() to read lootItems and partySize and send them to the server. The fetch POST happens in the background. If the server call works, the app only shows a message with setServerMessage(). It does not change lootItems or call updateUI() again. This order is important: one step changes data, another step saves it, and the last step shows it. If we mix them, the page can show old data or localStorage can save wrong data.

Why sync does not replace local persistence: saveState() saves to localStorage on every change, so the app still has data after a refresh. The server in syncToServer() is only for sharing or backup. It does not load data automatically when the page opens because loadFromServer() only runs when the user clicks the button. If the server is not available, the app still works from localStorage. localStorage is the fast local copy and the server is the shared external copy.

Validation during external load: loadFromServer() checks the server response with validateServerState() before it changes any data. That check makes sure state.loot is a list, state.partySize is a valid whole number and each item passes validateLootItem(). If any item fails the function returns null and does not change lootItems or partySize. This stops bad or harmful server data from replacing good state or making the app break halfway.

Debugging moment — console.log before assignment: During development I added console.log('server data before assign:', data) inside the .then() block of loadFromServer(), before calling validateServerState(data.state). This showed that the first test response had status: "empty" even though I had synced. The reason was a wrong studentId in the route. The log showed the server data clearly and proved the code order was right. Fixing STUDENT_ID to match the route and payload solved it.

A bug encountered and how lifecycle discipline fixed it: At first loadFromServer() called updateUI() before saveState(). The page showed the new loot but if the user refreshed, localStorage still had the old data and the app returned to the old state. The fix was to use this order: Fetch → Validate → Assign → Save → updateUI(). Now saveState() runs before updateUI() so localStorage and the page stay in sync. This rule made the bug easy to find: updateUI() ran before the data was saved.
